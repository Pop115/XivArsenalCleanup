# ArsenalCleanup

*Previously ArsenalExport; renamed 2026-09-06. The Dalamud plugin id changed with
it, so a settings file saved under the old name is not carried over — set the
export folder once after installing.*

A Dalamud plugin that exports everything your character can wear — the twelve
Armoury Chest containers **and the gear currently equipped** — to a structured
JSON file.

It reads through Dalamud's official `IGameInventory` API: no network capture, no
undocumented memory access.

## Why a plugin rather than a manual CSV export

Existing inventory tools can export a CSV, but they export item *names*. A
consumer then has to match those localised strings back to a game item, which
breaks on translations, HQ markers and near-identical names.

This plugin reads each piece's **item id** (`GameInventoryItem.BaseItemId`,
already stripped of the HQ/collectable offset) instead. Joining an export to the
game's own data becomes an exact integer equality rather than a text guess.

It also exports **worn gear**, which no Armoury Chest container holds. Gear on
the active job lives in a separate container, so an export built from the chest
alone silently omits, for every slot, the piece most likely to be the best one
owned — and a tool comparing item levels will happily crown a strictly inferior
piece "best available".

## Requirements

- XIVLauncher / Dalamud installed, and the game launched with Dalamud at least
  once (so `%AppData%\XIVLauncher\addon\Hooks\dev\` holds `Dalamud.dll`; with
  that in place, `DALAMUD_HOME` does not need to be set).
- .NET 10 SDK.

## Build

```bash
dotnet build ArsenalCleanup/ArsenalCleanup.csproj -c Release
```

This produces `ArsenalCleanup/bin/Release/ArsenalCleanup.dll` and
`ArsenalCleanup.json` (the manifest, generated by DalamudPackager from the
`.csproj` properties — there is no separate manifest file to maintain).

## Installing it as a dev plugin

1. In game, `/xlsettings` → **Experimental** tab → add the full path to
   `ArsenalCleanup.dll` to **Dev Plugin Locations**. This is a one-time step.
2. `/xlplugins` → **Dev Tools > Installed Dev Plugins** → enable "Arsenal
   Export".
3. After rebuilding, disable and re-enable the plugin in that tab: Dalamud does
   not hot-reload a DLL it has already loaded.

## Usage

- `/arsenalcleanup` — exports the character currently logged in.
- `/arsenalcleanupconfig` — opens the settings window (export folder).

`/arsenalexport` and `/arsenalexportconfig`, the names the plugin used before it
was renamed, still work. They are hidden from the command list so they do not
read as two separate features.

Exports go to the folder configured in the settings window. Leave it empty and
they land in an `exports` subfolder of the plugin's own Dalamud config
directory; the window shows the exact path. The chat message printed after each
export names the file that was written.

One file per character per day, named `yyyy-MM-dd-Character-Name-arsenal.json`.
Re-exporting the same character on the same day replaces that day's file rather
than piling up near-identical snapshots; previous days are left untouched. An
account with several characters needs one `/arsenalcleanup` per character, logged
in as each.

## Output format

```json
{
  "format_version": 1,
  "character": "Hero Example",
  "exported_at": "2026-09-06T18:30:00+02:00",
  "pieces": [
    { "slot": "main", "item_id": 31472, "quantity": 1, "is_hq": false,
      "is_collectable": false, "position": 0, "is_equipped": false },
    { "slot": "main", "item_id": 1688, "quantity": 1, "is_hq": false,
      "is_collectable": false, "position": 0, "is_equipped": true }
  ]
}
```

| Field | Meaning |
|---|---|
| `format_version` | Schema version. Check it and refuse what you do not understand — reading an older file field by field yields `undefined` everywhere instead of one legible error. |
| `slot` | Canonical slot name, one of `main`, `offhand`, `head`, `body`, `hand`, `legs`, `feet`, `ear`, `neck`, `wrist`, `ring`, `soul_crystal`. A stable ASCII key, never display text: it does not change with the client's language. |
| `item_id` | Base item id, HQ/collectable offset already removed. Joins directly against the game's `Item` sheet. |
| `quantity`, `is_hq`, `is_collectable` | As reported by the game. |
| `position` | Raw slot index inside the piece's own container. The game draws each Armoury tab in ascending index order, so a consumer can reproduce the layout the player actually sees. For worn gear this is the index in the equipped container. |
| `is_equipped` | True when the piece was on the character, false when it was in the Armoury Chest. |

Two entries can share a slot, a position and even an item id: one worn, one
stored. They are two distinct physical objects, and only the stored one can be
acted on without unequipping first — so consumers should keep them apart.

Equipped gear is one flat 14-entry array whose order is the game's own (the same
order as FFXIVClientStructs' `RaptureGearsetModule.GearsetItemIndex`, from main
hand at 0 to soul crystal at 13). Index 5 is the belt slot, removed from the game
years ago; it is skipped rather than exported under a guessed name.

## Design

`Plugin.cs` is the only file that touches live game state, and it holds no
decisions: which containers to visit, how a slot is named, how a file is named
and written all live in `ArmoryReader`, `ArmorySlot` and `ExportWriter`, which
run and are tested without a game.

`IInventorySource` exists for exactly that reason — the game sits behind a
one-method interface so the collection rules can be exercised against a fake
inventory.

## Tests

```bash
dotnet test ArsenalCleanup.Tests/ArsenalCleanup.Tests.csproj
```

With coverage:

```bash
dotnet test ArsenalCleanup.Tests/ArsenalCleanup.Tests.csproj \
  --settings coverlet.runsettings --collect:"XPlat Code Coverage"
```

The runsettings file restricts instrumentation to this assembly. Without it,
coverlet also instruments Dalamud and the whole of FFXIVClientStructs and reports
this plugin's coverage as a fraction of a percent.

`Plugin`, `ConfigWindow` and `Configuration.Save` are marked
`[ExcludeFromCodeCoverage]`: they are Dalamud wiring and ImGui draw calls that
cannot execute outside the game process. Everything else is covered.

The test project needs its own copy-local reference to `Dalamud.dll` (the plugin
itself references it with `Private="false"`, since the game process provides it
at runtime) to resolve `GameInventoryType` at test time — see the comment in
`ArsenalCleanup.Tests.csproj`.

## Known limitations

- One export covers one character: the one logged in when the command runs.
  There is no account-wide aggregation.
- Job levels are not exported. `IPlayerState.GetClassJobLevel(ClassJob)` could
  provide them without any extra dependency if a consumer ever needs them in the
  same file.
- Retainer and saddlebag inventories are not read.
